# RuntimePlan V6：编译器展开的 Boot

V6 在 V5 上只加一种计算：`boot_step`。编译器的 `expand-ckks-bootstrap` pass 可以把一条原生 `boot` 换成若干步，每一步是一条普通的计算指令，可以单独放到某张卡上、和别的指令并行，也可以在步与步之间插入 Transfer。V6 计划里仍可以有未展开的 `boot`；没有 `boot_step` 的计划仍然导出为 V5。

## 1. 指令

```json
{
  "ordinal": 12,
  "kind": "compute",
  "op": "boot_step",
  "place": {"kind": "device", "rank": 0, "index": 1},
  "inputs": ["40"],
  "output": "41",
  "attrs": {"operator_profile": "poseidon-gpu-degree58-da2-scale45",
            "step": "bsgs_group", "transform": "c2s", "layer": 0, "group": 3}
}
```

`operator_profile` 是 OperatorSpec 里一个 `implementation=native` 的 Boot profile。一步用到的密钥、明文常量和工作区都来自运行这一步的 Device 上的这个 profile，所以：

- `boot_step` 只能在 Device 上执行；
- 它不在 OperatorSpec 的 `operators` 表里登记，也不向计划要 Galois/relin 密钥；
- Runtime 要求 `boot_steps` 能力，Api 在 preflight 时确认每张卡都配置了这个 profile。

每一步都是两分量密文进、两分量密文出；`add`、`sub` 两个输入，其余一个输入。和 `boot` 一样，每一步在 `target_level`、`target_scale_log2` 里写明输出的 level 和 scale，Verifier 要求它们等于输出 ValueDesc（Api 在 `compute` 时看不到 ValueDesc）。

## 2. 各步

| step | 额外 attrs | 做什么 | level |
| --- | --- | --- | --- |
| `raise` | — | 原生 Boot 的 ModRaise 段：降到 q0+1、乘整数、rescale 到 q0、抬到完整 Q、改写 scale。S2C-first 的 profile（手写 ResNet20 Boot）输入已在 q0、scale 已由前一个 `mul_scalar` 定好，只抬到完整 Q、改写 scale | 不降低 |
| `rotate` | `steps` | 用 profile 的 Galois 密钥旋转 | 不变 |
| `conjugate` | — | 用 profile 的共轭密钥 | 不变 |
| `mul_const` | `key` | 乘 profile 里名为 `key` 的明文 | 不变 |
| `mul_scalar` | `multiplier` | 系数乘正整数，输出 scale 设为 `target_scale_log2` | 不变 |
| `set_scale` | — | 只把 scale 元信息改成 `target_scale_log2` | 不变 |
| `rescale` | `count` | 一次去掉 `count` 个 Q 素数（`rescale_many`），输出 scale 设为 `target_scale_log2` | 降 `count` |
| `linear` | `transform`、`layer` | CoeffToSlot（`c2s`）或 SlotToCoeff（`s2c`）的第 `layer` 层，按 profile 的线性变换模式执行并 rescale | 降低 |
| `bsgs_group` | `transform`、`layer`、`group` | 这一层第 `group` 个 giant 组：组内 baby 旋转共用一次 ModUp、在 QP 上累加、ModDown，再做 giant 旋转；不 rescale | 不变 |
| `eval_mod` | — | 整个 EvalMod | 降低 |
| `add`、`sub` | — | 两个同 level、同 scale 的密文相加、相减（求和，以及拆实部、虚部） | 不变 |

除 `target_level`、`target_scale_log2` 外，一步只能写它用到的 attrs，其他字段缺省（`steps=0`、`key=""`、`multiplier=0`、`count=0`、`transform` 无、`layer=-1`、`group=-1`），否则 reader 或 Verifier 拒绝。`rotate` 的 step 按 slot 数规范化后不能是 0。`mul_const` 的 key 写法由 profile 决定，Runtime 只把它交给 Api；Api 找不到就报错。

`mul_scalar`、`set_scale`、`rescale` 的输出 scale 在原生 Boot 里是直接赋值的，Api 照 `target_scale_log2` 设；其余各步的 scale 由 profile 的计算得出，Api 用实际结果和 ValueDesc 对照（`validate_value`）。

步的顺序由编译器按 profile 的 Boot 配方（gpu_api `make_boot_recipe` 导出）排出：配方第 1 版是 CtS-first（raise、c2s、拆实部虚部、两次 eval_mod、合并、s2c、输出），第 2 版的 `order=slot_to_coeff_first` 是先在输入上做 s2c，再 `mul_scalar`、raise、c2s、拆分、eval_mod，最后合并、乘折叠系数、加共轭、`set_scale`。两种顺序用的都是上表这些步。

MockVecApi 把整次 Boot 当作消息的恒等映射；展开后每一步都把第一个输入的 slot 原样传下去、元信息取 attrs，所以最后一步的输出就是 Boot 的输入，与未展开时一致。中间各步的 mock 值没有消息含义。

## 3. 计时

`RuntimeTiming.boot_step_calls` 和 `boot_step_nanoseconds` 单独记录这些步。`boot_calls` 仍只统计未展开的 `boot`。

## 4. 二进制

计算 op 码 12 是 `boot_step`，属性标签 5 依次是：u32 profile 字符串下标、u8 step（按上表顺序 0–11：raise、rotate、conjugate、mul_const、mul_scalar、set_scale、rescale、linear、bsgs_group、eval_mod、add、sub）、i32 target_level、float64 target_scale_log2、i32 steps、u32 key 字符串下标、u64 multiplier、i32 count、u8 transform（0 无、1 c2s、2 s2c）、i32 layer、i32 group，共 46 字节。
