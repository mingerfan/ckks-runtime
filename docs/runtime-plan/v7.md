# RuntimePlan V7：准备好的 API 调用

V7 在 [V5 的计划结构](README.md)上增加 `ApiCall`，用于执行后端已准备好的调用。输入 MLIR 已确定的 Rescale、Boot 和物理 level/scale 由这些调用实现；通用 Runtime 不重新规划、不补算术指令，也不隐式搬运数据。

当前 reader 支持 V1–V5 和 V7。V6 保留给独立的 BootStep 协议，仍明确拒绝；旧计划不自动升级成 V7。V7 沿用 V5 的有限 float64 scale：ValueDesc `scale_log2` 和 Rescale `target_scale_log2` 的表示及范围不变。

## JSON 指令

顶层使用 `"format_version":7`，其余结构沿用普通 RuntimePlan。ApiCall 仍是 Compute：

```json
{
  "ordinal": 0,
  "kind": "compute",
  "op": "ApiCall",
  "inputs": [],
  "output": "0",
  "place": {"kind": "device", "rank": 0, "index": 0},
  "attrs": {"callee": "stem", "call_id": "0"}
}
```

- `op` 必须恰为 `ApiCall`，不是 `api_call`。
- `callee` 是非空字符串，具体名称由外部调用 registry 定义，不是通用算术枚举。
- `call_id` 是无符号十进制**字符串**，除 `"0"` 外不允许前导零，匹配 `^(0|[1-9][0-9]*)$`，范围为 `0` 到 `18446744073709551615`。它标识外部准备的调用，不要求等于 ordinal 或 ValueId；不能写成 JSON number。
- `inputs` 可以为空，也可以有一个或多个 ValueId；`output` 始终是一个 ciphertext。
- `attrs` 只含 `callee`、`call_id`。未知字段、缺字段和重复 key 仍直接报错。

零输入允许准备好的 `stem` 使用预先加密并驻留的输入 patch。它不把 Device 密文变成 `external_inputs`；普通 external input 仍只能放在 Host。

## 物理元信息与生命周期

所有显式输入和输出必须是 ciphertext，且与指令同 Place、同 context。每个 ValueDesc 仍须通过 OperatorSpec 的 context、level 范围、模数预算和 components 等基础检查。

ApiCall **不要求输入之间 level 或 scale 相同**，也不套用普通加法、乘法、Rescale 或 Boot 的元信息公式。输出的 level、scale、NTT 和 components 由准备好的实现保证，并由 Api 的 `validate_value` 对照输出描述检查。例如，两个不同活动 Q 数的输入可以交给准备好的 residual add；不能因此改用普通 `add_cc` 的校验规则。

ApiCall 不查询 `OperatorSpec.operators` 的算术支持条目；即使 callee 名为 `bootstrap`，也不要求普通 Boot profile，不自动生成普通 Boot 能力或密钥要求。普通算术 op 和普通 `boot` 在 V7 中仍遵守原有规则。

ApiCall 禁止 `reuse_input`。内部工作区及融合由专用 Api 管理；该调用的计划内存回收只用普通 Release。SSA 定义、使用前定义、最终输出和 Release 规则不变：不能提前释放后再使用，也不能释放最终输出。异步调用必须自行保留已接手工作的输入，Runtime 可以在最后使用提交后丢掉自己的引用。

## 外部 registry 与专用 Api

RuntimePlan 只保存调用名、ID、SSA 依赖和物理描述，不序列化 callback、已加密输入、权重、密钥或内部工作区。调用方先建立外部 registry，由**明确实现 ApiCall 的专用 Api**按 `(callee, call_id)` 分发。通用 SequentialRuntime 仍调用 `api.compute(op, inputs)`；零输入不会走特殊的算术路径。

专用 Api 必须在启动/preflight 阶段确认调用 registry、目标设备/context、准备好的输入、密钥、工作区和所需能力可用。这些内部资源不能从不透明的调用名推导，通用 `PlanRequirements` 不代为声明或保证。未实现该调用的后端必须明确报不支持，不能静默透传、用普通算术代替或直接返回某个输入。

准备好的 GPU Boot 必须绑定真实的原生 Boot 实现，并检查外部准备配置与调用匹配。不能用解密再加密替代，也不能在原生实现失败后切换到解密再加密。`ApiCall` 本身不增加或选择普通 Boot 的 `implementation`/profile 字段。

## 二进制表示

容器版本和 magic 不变。ApiCall 使用 Compute instruction tag **1**、operator code **13**、attribute tag **6**。属性载荷固定 **12 bytes**：`u32 callee_string_index` 后接 `u64 call_id`，均为小端；不含 attribute tag 或其他 Compute 公共字段。callee 进入现有字符串表。

operator code **12** 和 attribute tag **5** 保留给 V6 BootStep，当前 reader 拒绝。这里的属性 tag 5 与现有 PreparePlaintext 的 instruction tag 5 无关。输入数组可为零长，`reuse-present` 必须为 0；Release 布局不变。完整容器与记录布局见[二进制格式](binary.md)。
