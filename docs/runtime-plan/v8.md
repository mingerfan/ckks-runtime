# RuntimePlan V8：Buffer 与 Device 外部密文

V8 在 [V7 ApiCall](v7.md) 上增加独立值类型 `ValueKind::Buffer`，用于共享后端的不透明中间结果，例如一次 hoist 生成、供多个 rotation suffix 使用的缓冲区。Buffer 有自己的 ValueId 和描述，不是伪装成 ciphertext 的工作区。

完整 JSON/二进制计划当且仅当至少含一个 Buffer，或 `external_inputs` 引用了 Device ciphertext 时使用 `format_version:8`。两项都没有的 V8 计划直接拒绝；只含 Host 外部输入、不含 Buffer 的计划沿用原有版本选择规则。Buffer 或 Device 外部密文出现在低于 V8 的计划中也拒绝。二进制 metadata 的空数组骨架单独解析，不是完整计划；版本条件在解码记录后针对完整计划检查。

V1–V5、V7 仍按原协议读取；V6 仍保留并拒绝。V8 沿用 V5/V7 的有限 float64 scale 和 V7 的 ApiCall，不引入 BootStep。

## JSON ValueDesc

```json
{
  "id": "8",
  "kind": "buffer",
  "place": {"kind": "device", "rank": 0, "index": 0},
  "context": "ctx-main",
  "level": 0,
  "scale_log2": 0,
  "ntt": false,
  "components": 0,
  "buffer_bytes": "4096",
  "buffer_layout": "rotation-hoist-v1"
}
```

- `kind` 必须为 `buffer`，对应 `ValueKind::Buffer`，二进制枚举值为 **2**。Buffer 只允许出现在 V8。
- 原有公共字段仍全部必填。Place 遵守普通规则；`context` 必须是同一 OperatorSpec 中实际存在的 context，不能使用占位名绕过检查。
- Buffer 固定使用 `level=0`、`scale_log2=0`、`ntt=false`、`components=0`。这些字段不表示 CKKS 密文元信息，不对 Buffer 套用模数预算或密文 components 规则。
- `buffer_bytes` 必填，是规范的 uint64 十进制**字符串**：匹配 `^(0|[1-9][0-9]*)$`，范围为 `0` 到 `18446744073709551615`。`"0"` 合法，不要求大于零；JSON number、符号、空白或前导零均不合法。
- `buffer_layout` 必填且为非空字符串。布局名称及其含义由专用后端定义，Runtime 不根据名称转换布局。
- CT/PT 的 JSON 结构完全不变，禁止出现 `buffer_bytes` 或 `buffer_layout`，即使写成 `"0"` 或空串也拒绝。内存中的 CT/PT 描述对应 `buffer_bytes=0`、`buffer_layout=""`。
- 未知字段、缺字段、重复 key 和其他非法描述直接报错，不猜测或修正。

V8 可以同时包含 CT、PT 和 Buffer；普通 CT/PT 算子仍遵守[通用规范](README.md)。

## 已驻留 Device 的外部密文

V8 的 `external_inputs` 可以引用已在指定 Device 上的 ciphertext，也保留 Host ciphertext 输入。调用方按 ValueId 提供实际对象；其 rank/device、context、level、scale、NTT 和 components 必须与描述一致。Runtime 在所属 rank 上验证并直接绑定该对象，不自动上传、不复制到另一个 Device、不添加 Transfer。后续调用仍必须同 Place；要换位置就显式通信。

这项放宽仅限 V8 的 ciphertext。V1–V5/V7 外部输入仍只允许 Host，所有版本的 plaintext 外部输入仍只允许 Host，Buffer 仍不能是外部输入。输入缺失、绑定多余或实际对象与描述不符都直接报错。没有 Buffer 的 Device 外部密文计划也使用 V8；仅有内部 Device 值不能触发 V8。文件的 JSON/二进制字段不变，所有 V8 CT/PT 描述仍写入下面规定的零字节数和空布局二进制后缀。

## ApiCall 和生命周期

ApiCall 的 JSON 字段不变：`op:"ApiCall"`，`attrs` 只含非空 `callee` 和规范 uint64 十进制字符串 `call_id`。它仍是单结果 Compute：

- `inputs` 可以为空，也可以有一个或多个输入。V8 的每个输入及输出可以是 CT 或 Buffer，不能是 PT；V7 的 CT-only 规则不变。
- 所有输入和输出必须同 context，Place 均与指令相同。零输入时也必须验证输出的 Place 和实际 context。
- ApiCall 不要求各 CT 输入的 level/scale 相同，不套用普通算术公式；输出物理描述由准备好的后端保证并校验。
- Buffer 只能由 ApiCall 产生、供 ApiCall 消费。Encode/Prepare、普通算术、Transfer、Replicate 都不能生成或使用 Buffer；Buffer 也不能列入 `external_inputs` 或 `final_outputs`。
- ApiCall 禁止 `reuse_input`，无论输入或输出是 CT 还是 Buffer。没有专用 Buffer 原位或通信路径。
- Buffer 遵守普通 SSA、使用前定义和 Release 规则。Release 不是一次数据使用，释放后不能再使用；不引入专用释放指令。

下面只列相关指令片段。`7` 是已定义 CT，`8` 是上面的 Buffer，`9` 和 `10` 是 CT；所有值均在 `ctx-main` 和同一 Device。callee 名称仅为示例，必须由外部 registry 实现。

```json
[
  {"ordinal":0,"kind":"compute","op":"ApiCall","place":{"kind":"device","rank":0,"index":0},"inputs":["7"],"output":"8","attrs":{"callee":"rotation_hoist","call_id":"0"}},
  {"ordinal":1,"kind":"compute","op":"ApiCall","place":{"kind":"device","rank":0,"index":0},"inputs":["8"],"output":"9","attrs":{"callee":"rotation_suffix","call_id":"1"}},
  {"ordinal":2,"kind":"compute","op":"ApiCall","place":{"kind":"device","rank":0,"index":0},"inputs":["8"],"output":"10","attrs":{"callee":"rotation_suffix","call_id":"2"}},
  {"ordinal":3,"kind":"release","value":"8"}
]
```

一份 hoist Buffer 供两个 suffix 共享，最后使用后才 Release，不为每个消费者复制一份。异步调用接手工作后必须自行保留输入；Runtime 按普通剩余使用次数和 Release 规则丢掉自己的引用，不代表设备工作已经完成。

## 后端与执行器

通用 Runtime 的接口不变：值表保存后端的 `Api::Value`，ApiCall 仍通过 `api.compute(op, inputs)` 执行，并由 `validate_value` 检查结果。后端可在自己的 Value variant 中加入 Buffer 对象，不需要新增执行器专用入口。

专用后端必须在启动/preflight 时检查 registry、目标 Place/context、Buffer 布局及所需能力、密钥和工作区。`validate_value` 必须确认实际 Buffer 对象与描述的 kind、Place/context、字节数和布局相符；不能把 CT 当作 Buffer，也不能接受不支持的布局。通用 `PlanRequirements` 不从 callee 或 layout 名称推导这些内部要求。不支持或不匹配就报错，不透传输入、不自动转换，也不改走普通算术。

完整原生 Boot 继续表示为不透明的 ApiCall，由后端绑定真实原生实现并检查配置。Buffer 不引入 BootStep，也不允许用解密再加密替代原生 Boot 或在失败后切换实现。其余 registry 和资源约定沿用 [V7](v7.md)。

## 二进制表示

容器版本及 magic 不变。V8 的**每个** ValueDesc 固定为 **51 bytes**，包括 CT/PT：

1. 原样保留 V5/V7 的 **39-byte 前缀**：`u64 id`、`u8 kind`、9-byte Place、`u32 context_string_index`、`i32 level`、`float64 scale_log2`、`u8 ntt`、`i32 components`。
2. 追加小端 `u64 buffer_bytes` 和 `u32 buffer_layout_string_index`。

Buffer 的 layout 引用非空字符串；CT/PT 的后缀必须为零字节数和空串引用。布局字符串全部进入现有字符串表，**包括空串**；空串引用不是缺省或特殊哨兵。V1–V4 的 35-byte、V5/V7 的 39-byte 描述布局不变。

ApiCall 的 Compute instruction tag **1**、operator code **13**、attribute tag **6** 均不变。属性载荷仍恰为 **12 bytes**：小端 `u32 callee_string_index` 后接 `u64 call_id`，不含属性 tag 或 Compute 公共字段。输入数组允许零长，`reuse-present` 必须为 0，Release 布局不变。

operator code **12** 和 attribute tag **5** 继续保留给 V6 BootStep，V8 也拒绝它们；PreparePlaintext 的 instruction tag 5 不受影响。完整偏移与容器规则见[二进制格式](binary.md)。
